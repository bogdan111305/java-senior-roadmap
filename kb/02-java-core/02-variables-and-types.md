Тема кажется базовой, но именно на ней строят вопросы на подвох: почему
`new Integer(200) == new Integer(200)` — `false`, а `Integer.valueOf(100) ==
Integer.valueOf(100)` — `true`. Ответ проверяет, понимает ли кандидат разницу
между примитивом и объектом-обёрткой и что скрывается за автобоксингом.

## Ключевые концепции

### Примитивы

#### Целочисленные и вещественные типы
В Java ровно восемь примитивных типов, и все они, кроме `boolean`, имеют
фиксированный, точно определённый спецификацией размер независимо от платформы
— в этом принципиальное отличие от языков вроде C, где размер `int` может
зависеть от компилятора и архитектуры. Целочисленная группа — `byte` (1 байт),
`short` (2 байта), `int` (4 байта) и `long` (8 байт) — все со знаком, потому что
в Java нет беззнаковых целых типов (кроме особого режима работы некоторых
операций, см. `>>>` в теме про операторы). Числа с плавающей точкой — `float`
(4 байта) и `double` (8 байт) — оба следуют стандарту IEEE 754, что означает не
только формат хранения (знак, экспонента, мантисса), но и наличие специальных
значений вроде `NaN` и `Infinity`, а также принципиальную неточность
представления многих десятичных дробей в двоичном виде (`0.1 + 0.2 != 0.3`).

#### char и boolean
`char` хранит не байт и не произвольный символ, а 16-битную беззнаковую code
unit кодировки UTF-16 — то есть по сути короткое целое число без знака в
диапазоне 0..65535. Из-за этого один `char` не всегда равен одному видимому
символу: символы за пределами Basic Multilingual Plane (например, многие эмодзи
и редкие иероглифы) в UTF-16 кодируются суррогатной парой из двух `char`, а не
одним, и код, который наивно проходит `String` по `char`, может разрезать такой
символ пополам. `boolean` — единственный примитив, для которого спецификация
JVM явно не фиксирует размер в байтах: логически это один бит, но на практике
JVM обычно хранит его как `int` (реализация зависит от конкретной виртуальной
машины и того, где именно переменная лежит — в стеке, в массиве или в поле
объекта).

### Обёртки и автобоксинг

#### Классы-обёртки
У каждого примитива есть класс-обёртка (`int` → `Integer`, `long` → `Long`,
`double` → `Double` и так далее) — обычный объект в куче, который хранит внутри
себя единственное `final`-поле с значением примитива. Как и `String`, все
обёртки неизменяемы: у `Integer` нет метода, который бы менял уже созданный
объект, любая «операция» над ним возвращает новый объект. Обёртки нужны там, где
требуется именно объект, а не примитив — прежде всего в generic-коллекциях
(`List<Integer>`, не `List<int>` — параметром типа в Java не может быть
примитив) и там, где важно отличить отсутствие значения (`null`) от значения по
умолчанию, которого у примитива просто нет.

#### Autoboxing, unboxing и Integer cache
Ручное оборачивание примитива в объект и обратно — рутина, поэтому компилятор
делает это автоматически: автобоксинг (autoboxing) неявно превращает примитив
в обёртку там, где по контексту ожидается объект, а автоunboxing — наоборот,
достаёт примитив из обёртки, где ожидается примитивное значение. Это чистый
синтаксический сахар компилятора: `Integer x = 5;` на уровне байткода
превращается в `Integer x = Integer.valueOf(5);`, а `int y = x;` — в
`int y = x.intValue();`. Именно через этот механизм и подключается один из
самых частых вопросов на собеседовании — Integer cache: `Integer.valueOf(int)`
для значений в диапазоне от -128 до 127 не создаёт новый объект при каждом
вызове, а возвращает один и тот же закэшированный экземпляр из внутреннего
статического массива, инициализированного один раз при загрузке класса
`Integer`. Для значений вне этого диапазона `valueOf` всегда создаёт новый
объект. Диапазон кэша по умолчанию — ровно -128..127, но верхнюю границу можно
расширить JVM-флагом `-XX:AutoBoxCacheMax` (нижняя фиксирована спецификацией).
Отсюда и разное поведение `==`: `==` для объектов сравнивает не значения, а
ссылки, поэтому два объекта из кэша — это буквально один и тот же объект в
памяти (`==` истинно), а два объекта, созданных вне кэша через `new` или через
`valueOf` за пределами диапازона, — разные объекты с одинаковым содержимым
(`==` ложно), хотя `equals` для них всё равно вернёт `true`. Автобоксинг литерала
(`Integer x = 100;`) внутри компилятор тоже превращает в `Integer.valueOf(100)`,
а не в `new Integer(100)` — именно поэтому два маленьких числа, присвоенных
через `=`, обычно оказываются одним и тем же объектом кэша, что и сбивает с
толку тех, кто не знает про кэш.

#### NullPointerException при unboxing
Обратная сторона автобоксинга — то, что он маскирует `null` под видом примитива.
Если переменная-обёртка равна `null`, а код пытается неявно распаковать её в
примитив (присвоить примитивной переменной, передать туда, где ожидается
примитив, использовать в арифметике), компилятор вставляет вызов `.intValue()`
(или аналога) на `null`-ссылке — и получается `NullPointerException` именно в
точке unboxing, а не там, где `null` был изначально присвоен. Это одна из самых
частых причин NPE в коде, который на первый взгляд вообще не похож на код,
работающий с `null`, — например, `Map<String, Integer>` без ключа отдаёт `null`,
и последующее `int x = map.get(key);` падает без каких-либо внешних признаков
проблемы в самой строке.

### Приведение типов

#### Widening и narrowing conversion
Преобразование одного числового типа в другой бывает двух принципиально разных
видов, и граница между ними — потенциальная потеря данных. Расширяющее
преобразование (widening conversion) идёт от типа меньшего диапазона к большему
(`byte → short → int → long → float → double`, а также `char → int`) и
происходит неявно, без приведения типа в коде, — компилятор гарантирует, что
значение поместится в новый тип без потери точности представления величины (хотя
при переходе от `long` к `float`/`double` теоретически возможна потеря точности
в младших разрядах мантиссы, сам факт «влезает по порядку величины»
гарантирован). Сужающее преобразование (narrowing conversion), наоборот, требует
явного приведения типа — `(int) someLong` — именно потому, что компилятор не
может гарантировать, что значение влезет в целевой тип без потерь: например,
`(int)` от `long`, превышающего диапазон `int`, просто отбрасывает старшие биты,
а `(int)` от `double` с дробной частью отбрасывает её целиком (обрезает, а не
округляет).

#### Переполнение (overflow)
Особый случай сужения — переполнение (overflow) внутри одного и того же по сути
диапазона: сложение двух `int`, результат которого не помещается в 32 бита, не
бросает исключение, а тихо «перескакивает» через границу диапазона за счёт
циклического переполнения в дополнительном коде (see also: темa про системы
счисления в разделе 1) — `Integer.MAX_VALUE + 1` даёт `Integer.MIN_VALUE`, а не
ошибку компиляции или исполнения. Это стоит держать в голове при работе с
идентификаторами, счётчиками и суммами — переход на `long` там, где величина
потенциально может вырасти, не самоочевиден и не проверяется компилятором
заранее.

#### var и вывод типа
Ключевое слово `var` (Java 10+) — это вывод типа на этапе компиляции (local
variable type inference), а не переход на динамическую типизацию: компилятор
сам определяет конкретный тип переменной по правой части выражения при
объявлении и подставляет его в байткод так, как будто тип был написан явно —
после компиляции никакой разницы между `var x = new ArrayList<String>();` и
`ArrayList<String> x = new ArrayList<String>();` не остаётся, и присвоить `var`
переменной позже значение несовместимого типа так же невозможно, как обычной
типизированной переменной. `var` работает только для локальных переменных с
инициализатором в той же строке — не для полей класса, параметров метода или
переменных без инициализации, — и её главная цель на практике: не дублировать
длинное имя generic-типа дважды в одной строке, а не «упростить» типизацию как
таковую.

## Примеры

```java
int max = Integer.MAX_VALUE;
System.out.println("Integer.MAX_VALUE = " + max);
System.out.println("MAX_VALUE + 1 = " + (max + 1));
```
```
Integer.MAX_VALUE = 2147483647
MAX_VALUE + 1 = -2147483648
```
Переполнение `int` не бросает исключение — значение молча «оборачивается» через
минимум диапазона. Именно поэтому счётчики и суммы, теоретически способные
превысить ~2.1 млрд, стоит с самого начала делать `long`.

```java
Integer a1 = new Integer(200);
Integer a2 = new Integer(200);
System.out.println("new Integer(200) == new Integer(200): " + (a1 == a2));

Integer b1 = Integer.valueOf(100);
Integer b2 = Integer.valueOf(100);
System.out.println("Integer.valueOf(100) == Integer.valueOf(100): " + (b1 == b2));

Integer c1 = Integer.valueOf(200);
Integer c2 = Integer.valueOf(200);
System.out.println("Integer.valueOf(200) == Integer.valueOf(200): " + (c1 == c2));
```
```
new Integer(200) == new Integer(200): false
Integer.valueOf(100) == Integer.valueOf(100): true
Integer.valueOf(200) == Integer.valueOf(200): false
```
`new Integer(...)` (конструктор с Java 9 объявлен deprecated к удалению) всегда
создаёт новый объект, поэтому `==` ложно даже для одинаковых значений внутри
диапазона кэша. `valueOf(100)` попадает в диапазон кэша -128..127 и возвращает
один и тот же объект — `==` истинно; `valueOf(200)` выходит за диапазон, и
каждый вызов создаёт новый объект — `==` снова ложно. Автобоксинг литерала
(`Integer d = 100;`) компилятор превращает именно в `valueOf`, а не в `new`,
поэтому ведёт себя так же, как явный `valueOf(100)`.

```java
double pi = 3.99;
System.out.println("(int) 3.99 = " + (int) pi);

long big = 4_294_967_296L; // 2^32
System.out.println("(int) 4294967296L = " + (int) big);
```
```
(int) 3.99 = 3
(int) 4294967296L = 0
```
`(int)` от `double` отбрасывает дробную часть целиком, а не округляет. `(int)`
от `long`, равного ровно 2^32, даёт 0 — старшие биты, не помещающиеся в 32-битный
`int`, просто отбрасываются, а оставшихся младших битов у этого конкретного
числа ровно ноль.

```java
Integer count = null;
int x = count; // неявный unboxing null
```
```
Exception in thread "main" java.lang.NullPointerException:
    Cannot invoke "java.lang.Integer.intValue()" because "<local1>" is null
	at Npe.main(Npe.java:4)
```
NPE возникает не в строке, где `count` получил `null`, а в строке присвоения
примитиву — именно там компилятор неявно вставил вызов `.intValue()`. Современный
JVM (Java 14+, "Helpful NullPointerExceptions") прямо называет, какой именно
вызов упал на `null`, что заметно упрощает диагностику по сравнению со старым
голым `NullPointerException` без деталей.

## Частые вопросы на собеседовании

**Q: Что произойдёт при переполнении int?**
A: Исключение не бросается — `int` переполняется циклически за счёт
представления чисел в дополнительном коде: `Integer.MAX_VALUE + 1` даёт
`Integer.MIN_VALUE`. Это тихая ошибка, которую легко пропустить в коде,
работающем со счётчиками или суммами, поэтому для величин, потенциально
способных превысить диапазон `int`, стоит сразу использовать `long`, а для
критичных мест — `Math.addExact`/`Math.multiplyExact`, которые бросают
`ArithmeticException` при переполнении вместо тихого оборачивания.

**Q: Почему new Integer(200) == new Integer(200) — false, а Integer.valueOf(100) == Integer.valueOf(100) — true?**
A: `new Integer(...)` всегда создаёт новый объект в куче, поэтому `==`,
сравнивающий ссылки, а не значения, даёт `false` для двух разных объектов даже
с одинаковым содержимым. `Integer.valueOf(int)` для значений от -128 до 127
возвращает объект из внутреннего статического кэша, инициализированного один
раз при загрузке класса `Integer`, — поэтому два вызова с одним и тем же
значением из этого диапазона возвращают буквально один и тот же объект, и `==`
для них истинно. Автобоксинг литералов компилятор реализует именно через
`valueOf`, а не через `new`, поэтому кэш затрагивает и обычное присваивание
`Integer x = 100;`.

**Q: Чем var отличается от динамической типизации?**
A: Ничем на уровне рантайма — `var` полностью разрешается компилятором в
конкретный тип по правой части выражения при объявлении переменной, и в
байткоде между `var x = 5;` и `int x = 5;` нет никакой разницы. Присвоить
переменной, объявленной через `var`, значение несовместимого типа позже так же
невозможно, как и обычной типизированной переменной — это вывод типа
(type inference) на этапе компиляции, а не отказ от статической типизации.

## Ловушки и частые ошибки

#### Сравнение обёрток через ==
Частая ошибка — считать, что кэш `Integer` работает для любых значений или что
`==` для обёрток в принципе можно использовать вместо `equals`. Кэш строго
ограничен диапазоном -128..127 (или шире, если явно поднята верхняя граница
флагом `-XX:AutoBoxCacheMax`), и код, который полагается на `==` для сравнения
значений `Integer`, работает «случайно правильно» только пока фигурируют
небольшие числа — на реальных данных (ID, суммы, счётчики за пределами кэша)
такой код тихо ломается. Сравнивать значения обёрток всегда нужно через
`equals` (или через сравнение распакованных примитивов).

#### Точность float/double
Другое заблуждение — считать, что `float`/`double` точно хранят десятичные
дроби вроде `0.1`. IEEE 754 — двоичное представление, и многие десятичные
дроби, конечные в десятичной системе, оказываются бесконечными периодическими
в двоичной — отсюда классический пример `0.1 + 0.2 != 0.3` (реально получается
`0.30000000000000004`). Для денежных расчётов, где точность критична,
используют `BigDecimal`, а не `double`/`float`.

#### Unboxing и NullPointerException
Ещё одна ловушка — считать unboxing безопасной операцией, которая просто
«достаёт число из коробки». Если обёртка равна `null`, unboxing бросает
`NullPointerException`, причём в точке распаковки, а не там, где `null` был
на самом деле присвоен переменной — это особенно неочевидно при работе с
`Map.get(...)`, который для отсутствующего ключа возвращает `null`, а не
значение по умолчанию.
