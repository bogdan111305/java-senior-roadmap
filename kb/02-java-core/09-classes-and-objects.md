Базовый синтаксис ООП в Java — то, с чего формально начинается язык, но именно
здесь закладываются детали, которые потом всплывают в более сложных темах:
порядок инициализации (следующая тема этого раздела), модификаторы доступа как
основа инкапсуляции (раздел 3) и то, почему конструктор по умолчанию не всегда
существует, даже если про него не думать явно.

## Ключевые концепции

### Конструкторы

#### Конструктор по умолчанию
Если класс не содержит ни одного явно объявленного конструктора, компилятор
сам генерирует конструктор без параметров (конструктор по умолчанию,
default constructor) — пустое тело, которое лишь неявно вызывает конструктор
родительского класса. Но это происходит только при полном отсутствии
конструкторов в классе: как только программист объявляет хотя бы один
конструктор — с параметрами или без — компилятор больше не генерирует
конструктор по умолчанию автоматически. Отсюда частая практическая ситуация:
класс с единственным конструктором, принимающим параметры, больше нельзя
создать вызовом `new SomeClass()` без аргументов — такой вызов просто не
скомпилируется, потому что подходящего конструктора не существует ни в
исходном коде, ни среди автоматически сгенерированных.

```java
public class NoDefault {
    NoDefault(int x) {}
    public static void main(String[] args) {
        NoDefault n = new NoDefault(); // конструктора без параметров нет
    }
}
```
```
NoDefault.java:4: error: constructor NoDefault in class NoDefault cannot be
    applied to given types;
        NoDefault n = new NoDefault();
                      ^
  required: int
  found:    no arguments
  reason: actual and formal argument lists differ in length
1 error
```
Как только в классе появился хотя бы один явный конструктор — здесь
`NoDefault(int x)` — компилятор больше не генерирует конструктор без
параметров автоматически. Попытка создать объект без аргументов ссылается на
конструктор, которого физически не существует ни в исходном коде, ни среди
сгенерированных.

#### this(...) и super(...): вызов другого конструктора
Внутри одного класса конструктор может вызвать другой конструктор того же
класса через `this(...)` — это позволяет вынести общую логику инициализации в
один «основной» конструктор, а остальные сделать тонкими обёртками с
значениями по умолчанию для части параметров. У этого механизма есть жёсткое
синтаксическое ограничение: вызов `this(...)` обязан быть самой первой
инструкцией в теле конструктора, если он вообще присутствует, — нельзя сначала
выполнить какую-то логику, а потом вызвать другой конструктор того же класса.
Такое же ограничение действует и для `super(...)` — явного вызова конструктора
родителя, который, если не написан явно, компилятор вставляет сам неявно
первой строкой (подробный разбор итогового порядка вместе с наследованием —
в следующей теме этого раздела).

```java
public class Point {
    int x, y;
    Point() {
        this(0, 0); // должен быть первой инструкцией тела конструктора
        System.out.println("Point() делегировал в Point(int,int)");
    }
    Point(int x, int y) {
        this.x = x;
        this.y = y;
        System.out.println("Point(int,int): x=" + x + " y=" + y);
    }
}
// вызов: new Point();
```
```
Point(int,int): x=0 y=0
Point() делегировал в Point(int,int)
```
Порядок вывода показывает, что тело `Point(int, int)` полностью отрабатывает
раньше, чем оставшаяся часть тела `Point()` после строки `this(0, 0)` — вызов
делегирует управление, а не просто «отмечается» и продолжает выполнение
параллельно.

#### Порядок инициализации внутри класса
Порядок инициализации внутри одного класса без наследования следует
фиксированной последовательности: сначала, один раз при первой загрузке
класса, выполняются static-блоки и static-инициализаторы полей в том
текстовом порядке, в котором они объявлены в исходном коде — как будто это
один слитый блок кода сверху вниз. Затем, при каждом создании объекта этого
класса — instance-инициализаторы полей и instance-блоки, тоже в порядке
объявления, и только после них — собственно тело конструктора. Из этого
следует, что поле, инициализированное значением, зависящим от другого поля,
объявленного ниже по тексту класса, на момент своей инициализации увидит это
другое поле ещё не инициализированным (со значением по умолчанию для его типа)
— порядок объявления в файле здесь имеет прямое семантическое значение, а не
только стилистическое.

```java
public class Obj {
    static { System.out.println("1. static-блок Obj"); }
    static int counter = initCounter();
    static int initCounter() { System.out.println("2. static-инициализатор поля counter"); return 0; }

    { System.out.println("3. instance-блок Obj"); }
    int id = initId();
    int initId() { System.out.println("4. instance-инициализатор поля id"); return 0; }

    Obj() {
        this(42);
        System.out.println("6. тело конструктора Obj()");
    }
    Obj(int x) {
        System.out.println("5. тело конструктора Obj(int) — вызван через this(42)");
    }

    public static void main(String[] args) {
        System.out.println("--- создаём первый объект ---");
        new Obj();
        System.out.println("--- создаём второй объект (static уже не повторится) ---");
        new Obj();
    }
}
```
```
1. static-блок Obj
2. static-инициализатор поля counter
--- создаём первый объект ---
3. instance-блок Obj
4. instance-инициализатор поля id
5. тело конструктора Obj(int) — вызван через this(42)
6. тело конструктора Obj()
--- создаём второй объект (static уже не повторится) ---
3. instance-блок Obj
4. instance-инициализатор поля id
5. тело конструктора Obj(int) — вызван через this(42)
6. тело конструктора Obj()
```
Static-блок и static-инициализатор поля выполнились ровно один раз, при первой
загрузке класса, ещё до первого `new Obj()`. При каждом создании объекта
instance-часть (блок и инициализатор поля) отрабатывает заново, в порядке
объявления, а тело `Obj()` фактически исполняется после тела `Obj(int)` — из-за
`this(42)` как первой инструкции управление сначала уходит во второй
конструктор, и только после его завершения продолжается тело первого.

### Модификаторы и структура

#### Четыре уровня видимости
У членов класса (полей, методов, вложенных классов) и самих классов в Java
четыре уровня видимости, и три из них обозначаются явными ключевыми словами,
а четвёртый — их отсутствием. `private` — виден только внутри самого класса,
самый строгий уровень инкапсуляции. `protected` — виден внутри пакета плюс во
всех подклассах, даже находящихся в других пакетах, — это специфика Java: во
многих других языках `protected` ограничен только иерархией наследования, а в
Java к ней добавляется ещё и доступ для всего родного пакета. `public` — виден
отовсюду, откуда в принципе видна сама точка, где объявлен модификатор.
Package-private (он же default, «доступ по умолчанию») — то, что получается,
если явный модификатор вообще не указан: виден только внутри того же пакета,
без учёта наследования за его пределами. Этот уровень видимости — единственный
в Java, у которого нет собственного ключевого слова, отсюда и распространённая
путаница у новичков, ищущих несуществующее слово «`default`» в объявлении поля.

```java
package com.example.bank;

public class Account {
    private double balance = 100.0;      // только внутри Account
    protected String ownerName = "Аня";  // пакет + подклассы в любом пакете
    public String id = "ACC-1";          // отовсюду
    double interestRate = 0.05;          // package-private: только внутри пакета com.example.bank

    void printFromInside() {
        System.out.println("balance (private, изнутри класса): " + balance);
    }
}
```
```java
package com.example.bank; // тот же пакет, что и Account

public class SamePackageReport {
    public static void main(String[] args) {
        Account acc = new Account();
        acc.printFromInside();
        System.out.println("ownerName (protected, тот же пакет): " + acc.ownerName);
        System.out.println("interestRate (package-private, тот же пакет): " + acc.interestRate);
        System.out.println("id (public): " + acc.id);
    }
}
```
```
balance (private, изнутри класса): 100.0
ownerName (protected, тот же пакет): Аня
interestRate (package-private, тот же пакет): 0.05
id (public): ACC-1
```
Внутри одного пакета доступны и `protected`, и package-private, и `public` поля
— `SamePackageReport` не является подклассом `Account`, но всё равно видит
`ownerName` именно благодаря принадлежности к тому же пакету. `private`-поле
`balance` при этом доступно только изнутри самого класса `Account`, что и
показывает метод `printFromInside()`.

### API

#### Пакеты и правило «один public-класс на файл»
Пакеты — не только пространство имён для избежания конфликтов классов с
одинаковыми именами, но и полноценная единица области видимости, участвующая
в модификаторах доступа напрямую (package-private и частично `protected`). На
уровне файловой системы (или `.jar`-архива) пакет соответствует физической
директории, и соглашение об именовании через обратный DNS-домен организации
(`com.example.project`) — не требование языка, а конвенция для гарантированной
уникальности пакетов между разными организациями и проектами. Отдельное
жёсткое правило компилятора: `.java`-файл может содержать не более одного
`public`-класса (интерфейса, enum), и если такой класс есть, имя файла обязано
точно совпадать с именем этого класса, включая регистр, — компилятор
отказывается компилировать файл, где это правило нарушено, ещё до какой-либо
попытки анализа логики кода. Non-public классов в одном файле при этом может
быть сколько угодно — ограничение касается именно `public`.

```java
public class WrongName { } // объявлен public class Foo внутри файла WrongName.java
```
```
WrongName.java:1: error: class Foo is public, should be declared in a file
    named Foo.java
public class Foo {
       ^
1 error
```
Компилятор отказывается компилировать файл ещё на этапе разбора имени класса
— несовпадение имени публичного класса с именем файла делает исходник
невалидным независимо от того, что написано внутри класса.

## Частые вопросы на собеседовании

**Q: Когда генерируется конструктор по умолчанию и когда — нет?**
A: Компилятор генерирует пустой конструктор без параметров только тогда, когда
в классе вообще не объявлено ни одного конструктора. Как только программист
пишет хотя бы один конструктор — с параметрами или без — автоматическая
генерация отключается полностью, и если нужен ещё и конструктор без
параметров, его придётся написать явно самому.

**Q: Чем protected в Java отличается от protected в языках вроде C++?**
A: В Java `protected` даёт доступ не только подклассам (в любом пакете), но и
всем классам того же пакета, даже не связанным наследованием, — то есть это
объединение «package-private плюс доступ для подклассов», а не чистое
ограничение только иерархией наследования, как в некоторых других языках.

**Q: Почему this() и super() обязаны быть первой строкой конструктора?**
A: Это гарантирует, что к моменту исполнения остального тела конструктора
объект уже прошёл цепочку инициализации родителя (через `super()`) либо
альтернативного конструктора того же класса (через `this()`) — иначе
конструктор мог бы обратиться к состоянию объекта (полям, унаследованным от
родителя, или ещё не выполненным instance-инициализаторам) до того, как оно
корректно установлено, что нарушало бы базовые инварианты порядка
инициализации, который подробно разбирается в следующей теме этого раздела.

## Ловушки и частые ошибки

#### «Конструктор по умолчанию есть всегда»
Частая ошибка — полагать, что конструктор по умолчанию существует всегда,
«на всякий случай», даже если в классе уже есть явные конструкторы. Это не
так (см. пример `NoDefault` выше), и рефакторинг, добавляющий в существующий
класс новый конструктор с параметрами, может незаметно сломать весь код,
создающий объекты этого класса без аргументов, если для этого явно не
оставлен отдельный конструктор без параметров.

#### package-private — это не «доступ не ограничен»
Другое заблуждение — путать package-private с полным отсутствием контроля
доступа, считая, что «раз модификатор не указан, значит доступ вообще не
ограничен». На самом деле это полноценный, самый частый по умолчанию (для
классов верхнего уровня) уровень видимости — просто ограниченный конкретно
пакетом, а не единственно возможным «открыто для всех», как `public`.

```java
package com.example.report; // ДРУГОЙ пакет, не наследник Account
import com.example.bank.Account;

public class OtherPackageReport {
    public static void main(String[] args) {
        Account acc = new Account();
        System.out.println("id (public): " + acc.id); // компилируется
        System.out.println("interestRate: " + acc.interestRate); // не компилируется
    }
}
```
```
OtherPackageReport.java:8: error: interestRate is not public in
    com.example.bank.Account; cannot be accessed from outside package
        System.out.println("interestRate: " + acc.interestRate);
                                                   ^
1 error
```
Из совершенно постороннего класса в другом пакете `id` (`public`) читается без
проблем, а `interestRate` (package-private) даже не компилируется — это
реальная, принудительно соблюдаемая компилятором граница, а не «отсутствие
модификатора» в смысле «без ограничений». По той же причине здесь не
скомпилировался бы и доступ к `ownerName` (`protected`) — `OtherPackageReport`
не подкласс `Account`, а всего лишь класс в другом пакете.

#### Инициализаторы полей vs instance-блоки
Похожая путаница — считать инициализаторы полей (`int x = compute();`) чем-то
принципиально отличным от instance-блоков (`{ ... }`). На уровне порядка
исполнения они полностью равноправны — компилятор трактует их как единую
последовательность инструкций в порядке объявления в классе (см. пример `Obj`
выше, где instance-блок и инициализатор поля `id` идут именно в порядке
объявления), просто инициализатор поля синтаксически привязан к конкретному
полю, а блок — самостоятельная конструкция; смешивать их в одном классе и
полагаться на порядок объявления — обычная и корректная практика.
