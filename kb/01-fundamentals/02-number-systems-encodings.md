Числа руками на собеседовании переводить не придётся, но эта тема объясняет
десяток практических вещей: почему `(byte) 0xFF` равно `-1`, почему
`Math.abs` может вернуть отрицательное число, почему `char` в Java — 16 бит и
откуда берутся «кракозябры» при неверно угаданной кодировке.

## Ключевые концепции

### Системы счисления

#### Двоичная, восьмеричная и шестнадцатеричная запись
Компьютер хранит всё в битах — двоичных разрядах, а восемь бит образуют байт
со значениями от 0 до 255. Позиционная система счисления с основанием `b`
записывает число цифрами от 0 до `b-1`, и каждая позиция весит в `b` раз
больше соседней справа: `101010₂ = 32 + 8 + 2 = 42`.

Длинные цепочки нулей и единиц читать неудобно, поэтому их группируют. Одна
шестнадцатеричная (hex) цифра — ровно 4 бита, одна восьмеричная — ровно 3.
Байт всегда записывается двумя hex-цифрами (`0x00`–`0xFF`), поэтому hex
встречается везде, где важна точность до байта: дампы памяти, хеши, UUID,
коды цветов, `.class`-файлы (`CAFEBABE`).

#### Перевод между системами
Из любой системы в десятичную переводят суммой цифр, умноженных на степени
основания. Из десятичной в другую — делением на основание с остатком: остатки,
прочитанные снизу вверх, и есть цифры результата
(`42 / 2 = 21 ост. 0`, `21 / 2 = 10 ост. 1`... → `101010`).

Между двоичной и hex переводят без арифметики, группировкой по 4 бита справа
налево: `0010 1010₂ = 2A₁₆`. В Java для этого есть готовые методы:
`Integer.toBinaryString`, `Integer.toHexString`, `Integer.parseInt(s, radix)`
и `HexFormat` (Java 17) для массивов байтов.

#### Литералы в Java
Java поддерживает литералы во всех трёх системах: `0b101010` — двоичный
(Java 7), `0x2A` — шестнадцатеричный, `052` — восьмеричный. Последний —
известная ловушка: ведущий ноль делает число восьмеричным, поэтому `010`
равно 8, а не 10. Длинные литералы можно разделять подчёркиванием:
`1_000_000`, `0xFF_FF`.

```java
System.out.println("0b101010=" + 0b101010 + " 0x2A=" + 0x2A + " 052=" + 052 + " 010=" + 010);
```
```
0b101010=42 0x2A=42 052=42 010=8
```
Одно и то же число 42 записано тремя способами, а `010` оказался восьмеричной
восьмёркой.

#### Дополнительный код (two's complement)
Отдельного бита «минус» в процессоре нет: отрицательные целые хранятся в
дополнительном коде. Чтобы получить `-x`, нужно инвертировать все биты `x` и
прибавить единицу. Поэтому `-1` — это все единицы, а старший бит работает как
знак.

Главное достоинство представления — сложение и вычитание выполняются одной
и той же схемой для любых знаков, процессору не нужна отдельная логика. Есть и
асимметрия: отрицательных значений на одно больше, чем положительных. У
`Integer.MIN_VALUE` нет положительной пары, поэтому `Math.abs(Integer.MIN_VALUE)`
и `-Integer.MIN_VALUE` возвращают тот же `Integer.MIN_VALUE`.

```java
System.out.println("-1 в двоичном: " + Integer.toBinaryString(-1));
System.out.println("Math.abs(Integer.MIN_VALUE)=" + Math.abs(Integer.MIN_VALUE));
```
```
-1 в двоичном: 11111111111111111111111111111111
Math.abs(Integer.MIN_VALUE)=-2147483648
```
`-1` в дополнительном коде — 32 единицы, а модуль минимального `int` остался
отрицательным: положительного числа такой величины в `int` нет.

#### Байты со знаком в Java
Все целые типы Java знаковые, включая `byte` с диапазоном от -128 до 127.
Поэтому байт `0xFF`, прочитанный из файла или сети, в переменной `byte`
равен `-1`. Чтобы получить беззнаковое значение 0–255, байт маскируют:
`b & 0xFF` или `Byte.toUnsignedInt(b)`.

Без маски при расширении до `int` знаковый бит размножается (sign extension),
и вместо 255 получается -1. Это частая ошибка при разборе бинарных протоколов,
вычислении контрольных сумм и переводе байтов в hex.

```java
byte b = (byte) 0xFF;
System.out.println("(byte)0xFF=" + b + ", b & 0xFF=" + (b & 0xFF) + ", Byte.toUnsignedInt=" + Byte.toUnsignedInt(b));
```
```
(byte)0xFF=-1, b & 0xFF=255, Byte.toUnsignedInt=255
```
Байт `0xFF` в Java равен `-1`, а беззнаковое 255 получается только маской.

#### Порядок байтов (endianness)
Многобайтовое число можно записать в память двумя способами. Big-endian —
старший байт первым: `0x0A0B0C0D` хранится как `0A 0B 0C 0D`. Little-endian —
младший байт первым: `0D 0C 0B 0A`.

Процессоры x86 и большинство ARM работают в little-endian, а сетевые протоколы
и формат `.class`-файлов используют big-endian («сетевой порядок байтов»).
Java скрывает это от программиста: `DataOutputStream` и `ByteBuffer` по
умолчанию пишут big-endian. Но при чтении чужого бинарного формата порядок
нужно знать и задать явно — `ByteBuffer.order(ByteOrder.LITTLE_ENDIAN)`.

```java
ByteBuffer big = ByteBuffer.allocate(4).putInt(0x0A0B0C0D);
ByteBuffer little = ByteBuffer.allocate(4).order(ByteOrder.LITTLE_ENDIAN).putInt(0x0A0B0C0D);
System.out.println("big-endian:    " + Arrays.toString(big.array()));
System.out.println("little-endian: " + Arrays.toString(little.array()) + ", native=" + ByteOrder.nativeOrder());
```
```
big-endian:    [10, 11, 12, 13]
little-endian: [13, 12, 11, 10], native=LITTLE_ENDIAN
```
`ByteBuffer` по умолчанию пишет big-endian, хотя сам процессор
little-endian.

### Кодировки текста

#### ASCII и Unicode
Кодировка — правило перевода символов в байты и обратно. ASCII использует
7 бит и содержит 128 символов: латиницу, цифры, знаки препинания и
управляющие символы. Для остальных языков появились однобайтовые кодировки
вроде Windows-1251 и KOI8-R, в которых одни и те же байты означают разные
символы.

Unicode решает проблему на уровне идеи: это единая таблица, где у каждого
символа всех письменностей есть номер — code point, от `U+0000` до `U+10FFFF`.
Сам Unicode не говорит, как хранить эти номера в байтах; это задача
конкретных кодировок — UTF-8, UTF-16, UTF-32.

#### UTF-8
UTF-8 — кодировка переменной длины: от 1 до 4 байт на символ. Символы ASCII
занимают один байт и совпадают с ASCII побайтно, поэтому UTF-8 обратно
совместима с ним. Кириллица занимает 2 байта, большинство остальных символов
BMP — 3, эмодзи и редкие иероглифы — 4.

Длина символа видна по старшим битам первого байта: `0xxxxxxx` — один байт,
`110xxxxx` — начало двухбайтового, `1110xxxx` — трёхбайтового, `11110xxx` —
четырёхбайтового. Все байты-продолжения начинаются с `10`. Благодаря этому
UTF-8 самосинхронизируется: по любому байту понятно, начало это символа или
середина. UTF-8 — стандарт де-факто для веба, JSON, HTTP и файлов.

Сколько байт занимает символ:
```java
for (String s : new String[]{"A", "Ж", "€", "😀"}) {
    byte[] utf8 = s.getBytes(StandardCharsets.UTF_8);
    // печатаем байты в hex и s.length()
}
```
```
A -> UTF-8 1 байт: 41 | UTF-16 char: 1
Ж -> UTF-8 2 байт: D0 96 | UTF-16 char: 1
€ -> UTF-8 3 байт: E2 82 AC | UTF-16 char: 1
😀 -> UTF-8 4 байт: F0 9F 98 80 | UTF-16 char: 2
```
Видна структура UTF-8: первый байт `D0` начинается с битов `110` (двухбайтовый
символ), `E2` — с `1110` (трёхбайтовый), `F0` — с `11110` (четырёхбайтовый).
Эмодзи занимает 4 байта в UTF-8 и два `char` в Java.

#### UTF-16 и Java char
UTF-16 кодирует символ одной или двумя 16-битными единицами (code units).
Символы основной плоскости (BMP, `U+0000`–`U+FFFF`) занимают одну единицу, а
символы за её пределами — пару единиц, суррогатную пару. API строк Java
построено на UTF-16: `char` — это одна 16-битная code unit, а не «символ» в
бытовом смысле.

Поэтому у эмодзи `"😀".length()` равно 2: строка содержит два `char`, хотя
символ один. Для работы с настоящими символами есть методы по code points:
`codePointCount`, `codePointAt`, `codePoints()`.

Внутреннее хранение `String` с Java 9 устроено иначе (Compact Strings, JEP 254):
если все символы строки укладываются в Latin-1, она хранится как массив байтов
по одному байту на символ, иначе — по два байта в UTF-16. Это деталь
реализации для экономии памяти, а API по-прежнему работает в терминах UTF-16
(тема «Строки» раздела 2).

#### Mojibake
Если байты декодировать не той кодировкой, в которой их записали, получится
mojibake — «кракозябры». Текст «Привет», записанный в UTF-8 и прочитанный как
Windows-1251, превращается в `РџСЂРёРІРµС‚`: каждый двухбайтовый символ UTF-8
читается как два отдельных символа однобайтовой кодировки.

Обратная ситуация опаснее. Байты Windows-1251 не являются корректной
последовательностью UTF-8, и декодер заменяет их символом `U+FFFD` (`�`). Такая
потеря необратима: исходные байты из строки уже не восстановить.

Mojibake в обе стороны:
```java
byte[] bytes = "Привет".getBytes(StandardCharsets.UTF_8);
System.out.println("UTF-8 -> cp1251: " + new String(bytes, Charset.forName("windows-1251")));
byte[] cp = "Привет".getBytes(Charset.forName("windows-1251"));
System.out.println("cp1251 -> UTF-8: " + new String(cp, StandardCharsets.UTF_8));
```
```
UTF-8 -> cp1251: РџСЂРёРІРµС‚
cp1251 -> UTF-8: ������
```
В первом случае текст испорчен, но байты сохранены: если прочитать их
правильной кодировкой, «Привет» вернётся. Во втором декодер заменил
некорректные последовательности на `�`, и исходные данные потеряны.

#### Кодировка по умолчанию в Java
До Java 17 включительно кодировка по умолчанию зависела от ОС и локали: на
Linux обычно UTF-8, на русской Windows — Windows-1251. Код без явной
кодировки (`new String(bytes)`, `FileReader`, `getBytes()`) вёл себя по-разному
на разных машинах.

С Java 18 (JEP 400) кодировка по умолчанию — UTF-8 на всех платформах.
Кодировка ОС осталась доступна через свойство `native.encoding`, а вывод в
консоль управляется отдельным свойством `stdout.encoding`. Тем не менее
кодировку стоит указывать явно (`StandardCharsets.UTF_8`): код может
запускаться на старой JVM или с переопределённым `file.encoding`.

JDK 21 на русской Windows:
```java
System.out.println("defaultCharset=" + Charset.defaultCharset()
        + ", native.encoding=" + System.getProperty("native.encoding"));
```
```
defaultCharset=UTF-8, native.encoding=Cp1251
```
Кодировка ОС — `Cp1251`, но кодировка по умолчанию в Java 21 — UTF-8.

### Двоичные данные в тексте

#### Base64
Base64 — не кодировка символов, а способ записать произвольные байты
текстом, который безопасно передаётся через JSON, HTTP-заголовки, email и URL.
Каждые 3 байта (24 бита) превращаются в 4 символа из алфавита в 64 символа,
поэтому данные вырастают примерно на треть, а неполный хвост добивается
символами `=`.

Обычный алфавит Base64 содержит `+` и `/`, которые имеют особый смысл в URL,
поэтому для URL и JWT используют вариант URL-safe с `-` и `_`. В Java оба
варианта есть в `java.util.Base64`. Важно помнить, что Base64 — не
шифрование: любой декодирует его обратно одной строкой.

```java
System.out.println(Base64.getEncoder().encodeToString("Hi?".getBytes(StandardCharsets.UTF_8)));
byte[] raw = {(byte) 0xFB, (byte) 0xFF};
System.out.println(Base64.getEncoder().encodeToString(raw) + " / " + Base64.getUrlEncoder().encodeToString(raw));
```
```
SGk/
+/8= / -_8=
```
Три байта `Hi?` превратились ровно в четыре символа без `=`. Для двух байт
`FB FF` обычный Base64 выдал `+` и `/`, URL-safe — `-` и `_`, а хвост добит `=`.

## Частые вопросы на собеседовании

**Q: Почему `"😀".length()` в Java равен 2, а не 1?**
A: `String.length()` считает `char`, то есть 16-битные code units UTF-16, а не
символы. Эмодзи лежит за пределами BMP и кодируется суррогатной парой из двух
`char`. Число настоящих символов возвращает `codePointCount`, а перебирать их
нужно через `codePoints()`.

**Q: Чем UTF-8 отличается от UTF-16?**
A: Обе кодировки покрывают весь Unicode и имеют переменную длину. UTF-8
использует от 1 до 4 байт и совместима с ASCII, поэтому она компактнее для
латиницы и стала стандартом для передачи данных. UTF-16 использует 2 или 4
байта; на ней построены API строк Java, JavaScript и Windows.

**Q: Почему `Math.abs(Integer.MIN_VALUE)` отрицательное?**
A: В дополнительном коде диапазон `int` — от -2³¹ до 2³¹-1, и у минимального
значения нет положительной пары. Операция переполняется и возвращает тот же
`Integer.MIN_VALUE`. Если важно не пропустить такой случай, используют
`Math.absExact`, который бросает `ArithmeticException`.

**Q: Как правильно прочитать беззнаковый байт в Java?**
A: Тип `byte` знаковый, поэтому значения от 128 до 255 превращаются в
отрицательные. Беззнаковое значение получают маской `b & 0xFF` или
`Byte.toUnsignedInt(b)`. Для `int` и `long` есть аналогичные методы
`Integer.toUnsignedLong`, `Long.toUnsignedString` и беззнаковое сравнение
`Integer.compareUnsigned`.

**Q: Base64 — это шифрование?**
A: Нет, это кодирование байтов в текст без какого-либо ключа. Он нужен, чтобы
передать двоичные данные через текстовые каналы. Любой может декодировать
Base64 обратно, поэтому секреты в нём «спрятать» нельзя — как и в payload JWT.

## Ловушки и частые ошибки

#### char — это не всегда один символ
Код, который перебирает строку по `char` или берёт `s.charAt(i)`, может
разрезать суррогатную пару пополам. Тогда `substring` возвращает строку с
половинкой эмодзи, а «разворот» строки по `char` превращает её в мусор. Для
пользовательского текста работают с code points.

#### Не указывать кодировку явно
С Java 18 кодировка по умолчанию — UTF-8, но полагаться на это стоит
осторожно. Код может работать на Java 8–17, где кодировка зависит от ОС, или
с явно переопределённым `-Dfile.encoding`. Явное `StandardCharsets.UTF_8`
делает поведение одинаковым везде.

#### Знаковый byte при разборе бинарных данных
`int value = bytes[i]` для байта `0xC8` даёт -56, а не 200. Ошибка
проявляется только на значениях больше 127, поэтому тесты на «простых»
данных её не ловят. Любой байт из внешнего источника перед использованием
как число нужно маскировать `& 0xFF`.

#### Ведущий ноль в литерале
`int code = 010;` — это 8. Ведущие нули часто появляются при копировании кодов
вида «007» или дат в код, и ошибка не видна при чтении. Если число пришло из
строки, `Integer.parseInt("010")` вернёт 10 — разбор строк восьмеричную
запись не учитывает.
