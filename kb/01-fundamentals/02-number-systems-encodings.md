# Системы счисления и кодировки

---
Важно не для того, чтобы переводить числа руками, а чтобы понимать, почему в Java
`char` — это 16 бит, как работают битовые операции и откуда берётся mojibake при
неверно угаданной кодировке.

## Ключевые концепции

### Системы счисления
Компьютер физически оперирует только двоичными значениями, но читать длинные
цепочки нулей и единиц человеку неудобно, поэтому в коде и логах их компактно
записывают в восьмеричной или, чаще, шестнадцатеричной (hex) системе — каждая
hex-цифра кодирует ровно 4 бита, а каждая восьмеричная — 3, так что перевод между
ними сводится к простой группировке битов справа налево, без арифметики. Hex особенно
часто встречается там, где важна компактность и точное совпадение по байтам: в
memory dump, UUID, хэш-строках, кодах цветов.

Отдельный вопрос — как представить отрицательные числа в двоичном виде, ведь бита
для «минуса» отдельно нет. Для этого используется дополнительный код (two's
complement): он устроен так, что сложение и вычитание работают по одним и тем же
правилам что для положительных, что для отрицательных чисел — процессору не нужна
отдельная логика для знака. У этого представления есть характерное асимметричное
следствие: отрицательных чисел на единицу больше, чем положительных, и у самого
маленького отрицательного числа (`Integer.MIN_VALUE`) просто нет положительной пары
того же размера — поэтому `Math.abs(Integer.MIN_VALUE)` переполняется и молча
возвращает тот же `Integer.MIN_VALUE`, а не положительное число.

### Кодировки текста
Кодировка — это правило, по которому символ переводится в последовательность байтов
и обратно. Первой массовой кодировкой была ASCII: всего 7 бит на символ, из-за чего
в неё влезает только латиница и управляющие символы — никакой кириллицы, иероглифов
и так далее. Unicode решает эту проблему на уровне идеи: это просто таблица code
points — числовых идентификаторов для символов всех языков и алфавитов, — но сам по
себе Unicode ничего не говорит о том, как именно эти числа хранить в байтах, это
отдельный вопрос.

На этот вопрос отвечают конкретные кодировки. UTF-8 — кодировка переменной длины
(от 1 до 4 байт на символ), обратно совместимая с ASCII, и поэтому она стала
стандартом для передачи данных: JSON, HTTP-тела и большинство файлов в вебе сегодня
в UTF-8. Внутри самой Java используется другая кодировка — UTF-16, тоже переменной
длины (2 или 4 байта через так называемые суррогатные пары). Это прямо влияет на
работу со строками в языке: Java-тип `char` — это не «символ» в бытовом смысле, а
одна 16-битная UTF-16 code unit. Из-за этого у символов за пределами Basic
Multilingual Plane — например, у многих эмодзи — `String.length()` возвращает 2, а
не 1: сам символ на самом деле хранится как пара `char`.

Когда байты декодируют кодировкой, отличной от той, в которой их закодировали
(например, записали текст в UTF-8, а прочитали как Windows-1251), результат
превращается в нечитаемый набор символов — это явление называют mojibake, и именно
оно стоит за классическими «кракозябрами» вместо текста.

## Примеры
```java
System.out.println(Integer.toBinaryString(42));
System.out.println(Integer.toHexString(42));
System.out.println(Integer.parseInt("2a", 16));
```
Вывод:
```
101010
2a
42
```
`toBinaryString`/`toHexString` показывают представление числа в другой системе
счисления, а `parseInt(str, 16)` делает обратную операцию — превращает
hex-строку обратно в `int`. Обратите внимание на разницу в компактности: `42` в
двоичном виде — это `101010`, шесть символов, а в hex — всего `2a`, два символа;
именно поэтому hex и используют там, где двоичную запись неудобно читать глазами.

```java
String s = "😀";
System.out.println(s.length());
System.out.println(s.codePointCount(0, s.length()));
```
Вывод:
```
2
1
```
`length()` в Java считает `char`, а не «символы» в бытовом смысле. Эмодзи 😀 не
входит в Basic Multilingual Plane и кодируется суррогатной парой из двух `char`,
поэтому `length()` возвращает 2. `codePointCount`, наоборот, считает реальные
codepoints — то есть настоящие символы — и корректно возвращает 1.

## Частые вопросы на собеседовании
**Q: Почему `"😀".length()` в Java равен 2, а не 1?**
A: `String.length()` считает `char`, то есть 16-битные UTF-16 code units, а не
codepoints. Символы за пределами Basic Multilingual Plane кодируются суррогатной
парой из двух `char`. Чтобы получить реальное число символов, нужно `codePointCount`.

## Ловушки и частые ошибки
Самая частая ошибка — считать, что `char` в Java всегда равен одному символу. На
самом деле это 16-битная UTF-16 code unit, и для codepoints за пределами BMP один
видимый символ занимает два `char` подряд — код, который перебирает строку по
`char` или берёт `s.charAt(i)`, может разрезать такой символ пополам.

Вторая частая ошибка — не указывать кодировку явно при чтении и записи файлов или
сокетов, полагаясь на кодировку по умолчанию. Она платформозависима и отличается
между ОС (например, между Linux и Windows), поэтому код без явной кодировки может
годами работать «у меня на машине» и ломаться при переносе на другую платформу.
