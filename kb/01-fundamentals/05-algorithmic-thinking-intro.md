# Алгоритмическое мышление: введение

---
Точка входа перед структурами данных и сложностью — чтобы фраза "какая сложность у
этого решения" была не пустым звуком, а реальным инструментом сравнения подходов.

## Ключевые концепции

### Основные понятия
Алгоритм — это просто конечная последовательность шагов, решающая конкретную
задачу. Разных алгоритмов для одной и той же задачи может быть много, и они могут
сильно отличаться по тому, сколько времени и памяти требуют на больших входных
данных. Чтобы сравнивать решения между собой независимо от конкретного железа,
языка программирования и версии компилятора, используют оценку сложности — язык,
который абстрагируется от constant-факторов и говорит именно о том, как растёт
потребление ресурсов с ростом размера входных данных.

Для этой оценки есть три обозначения, которые часто путают. `O()` — асимптотическая
верхняя граница, «не хуже, чем...» — то есть гарантия, что алгоритм не будет
работать медленнее некоторой функции от размера входа. `Ω()` — нижняя граница, «не
лучше, чем...» — симметричная гарантия снизу. `Θ()` — точная оценка, когда верхняя
и нижняя границы совпадают, то есть алгоритм действительно растёт именно с такой
скоростью, не быстрее и не медленнее. На практике в разговоре почти всегда говорят
просто «O()», даже когда по строгому математическому определению имеют в виду `Θ` —
это общепринятое упрощение, а не ошибка, но полезно знать, что формально это разные
вещи.

Кроме времени выполнения у алгоритма есть ещё одна важная характеристика — сколько
дополнительной памяти он потребляет сверх самих входных данных, это называется
сложностью по памяти (space complexity). Например, сортировка на месте (in-place)
почти не использует дополнительную память — её space complexity O(1), тогда как
merge sort для своей работы создаёт дополнительные массивы того же порядка, что и
исходные данные — его space complexity O(n). На собеседовании об этом часто
забывают, оценивая только скорость, хотя реальный выбор алгоритма почти всегда —
компромисс между временем и памятью.

Наконец, прежде чем писать код, полезно явно проговорить декомпозицию — разбить
задачу на подзадачи и описать план псевдокодом. Это не формальность: на живом
собеседовании декомпозиция вслух показывает ход мысли интервьюеру и страхует от
того, чтобы начать писать код «с наскока», упереться в забытый edge case на
середине и переписывать половину решения заново.

## Примеры
```java
// O(1) — не зависит от размера входных данных
int first(int[] arr) { return arr[0]; }

// O(n) — один проход по входным данным
int sum(int[] arr) {
    int total = 0;
    for (int x : arr) total += x;   // n итераций
    return total;
}

// O(n^2) — вложенный цикл по тем же данным (классический наивный поиск дублей)
boolean hasDuplicate(int[] arr) {
    for (int i = 0; i < arr.length; i++)
        for (int j = i + 1; j < arr.length; j++)
            if (arr[i] == arr[j]) return true;
    return false;
}

System.out.println(hasDuplicate(new int[]{1, 5, 3, 9}));       // false — 4 элемента, 6 сравнений
System.out.println(hasDuplicate(new int[]{1, 5, 3, 9, 5}));    // true  — 5 элементов, до 10 сравнений
```
Вывод:
```
false
true
```
Разница в размере входа всего на один элемент (4 → 5), а число возможных сравнений
в худшем случае выросло с 6 до 10 — это и есть O(n²) не в теории, а на конкретных
числах: при удвоении размера массива количество сравнений вырастет примерно вчетверо,
а не вдвое.

Декомпозиция на псевдокоде (пример разговора на собеседовании перед кодом):
```
найти второй по величине элемент массива:
  1. если элементов меньше двух — некорректный ввод, обработать отдельно
  2. пройти массив один раз, храня max и secondMax
  3. на каждом шаге: если x > max — secondMax = max, max = x
                      иначе если x > secondMax — secondMax = x
  4. вернуть secondMax  → O(n) по времени, O(1) по памяти
```

## Частые вопросы на собеседовании
**Q: Чем отличаются O(), Ω() и Θ()?**
A: `O()` — верхняя граница роста функции (худший или общий случай, "не хуже, чем"),
`Ω()` — нижняя граница ("не лучше, чем"), `Θ()` — точная асимптотика, когда верхняя и
нижняя оценки совпадают. В повседневной речи разработчики почти всегда используют
"O()" в значении "типичная/точная сложность", хотя формально это не всегда `Θ`.

## Ловушки и частые ошибки
Частая ошибка — считать, что O(n) всегда быстрее O(n²) на практике. Это не всегда
так на малых `n`: big-O скрывает константные множители, и алгоритм с формально
худшей асимптотикой может реально работать быстрее на небольших входных данных —
классический пример: insertion sort нередко быстрее merge sort на маленьких
массивах, несмотря на худшую асимптотику.

Вторая частая ошибка — оценивать только время выполнения и забывать про сложность
по памяти. На собеседовании нередко спрашивают именно про этот trade-off — «можно
решить быстрее, но за счёт памяти» — и ожидают, что кандидат сам о нём вспомнит, а
не только после наводящего вопроса.
