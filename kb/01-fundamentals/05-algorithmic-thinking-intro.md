Точка входа перед структурами данных и сложностью — чтобы фраза «какая
сложность у этого решения» была не пустым звуком, а реальным инструментом
сравнения подходов. На собеседовании оценку сложности просят почти к каждой
задаче, а senior-уровень видно по тому, как кандидат говорит о компромиссе
между временем и памятью.

## Ключевые концепции

### Основные понятия

#### Что такое алгоритм и сложность
Алгоритм — конечная последовательность шагов, решающая конкретную задачу. Для
одной задачи алгоритмов бывает много, и на больших входных данных они могут
отличаться по времени и памяти в тысячи раз.

Чтобы сравнивать решения независимо от железа, языка и компилятора, используют
асимптотическую оценку сложности. Она отбрасывает константы и младшие члены и
описывает только то, как растёт потребление ресурсов с ростом размера входа
`n`. Алгоритм, делающий `3n² + 10n + 7` операций, имеет сложность O(n²): при
больших `n` всё остальное перестаёт влиять.

#### O(), Ω(), Θ()
Для этой оценки есть три обозначения. `O(f(n))` — асимптотическая верхняя
граница: функция растёт не быстрее `f(n)` с точностью до константы. `Ω(f(n))` —
нижняя граница: растёт не медленнее. `Θ(f(n))` — точная оценка, когда верхняя
и нижняя границы совпадают.

В разговоре почти всегда говорят «O», даже когда по смыслу имеют в виду Θ:
«поиск в массиве — O(n)» обычно означает «растёт линейно». Это принятое
упрощение, но формально O(n²) тоже верхняя граница для линейного поиска,
просто неточная.

#### Худший, средний и лучший случай
Отдельный вопрос — для каких входных данных мы оцениваем алгоритм. У
быстрой сортировки лучший и средний случай — n log n, а худший — n²
(например, на уже отсортированных данных при неудачном выборе опорного
элемента). У поиска в `HashMap` в среднем O(1), а в худшем, когда все ключи
попали в одну корзину, — O(n) или O(log n) после превращения корзины в дерево.

Важно не путать два разных измерения. Худший, средний и лучший случай — это
про входные данные. O, Ω и Θ — про то, как описывается рост функции. Можно
сказать «худший случай быстрой сортировки — Θ(n²)» и «лучший случай —
Θ(n log n)»; утверждение «O — это худший случай» — распространённая, но
неверная формулировка.

#### Амортизированная сложность
Иногда отдельная операция бывает дорогой, но редко. `ArrayList.add` обычно
просто кладёт элемент в массив за O(1), но когда массив заполнен, создаётся
новый, в 1,5 раза больше, и все элементы копируются — это O(n).

Амортизированная оценка усредняет стоимость по длинной последовательности
операций. Раз дорогие расширения происходят всё реже (ёмкость растёт
геометрически), суммарная стоимость `n` добавлений — O(n), то есть O(1) в
среднем на операцию. Это не «средний случай» по входным данным, а гарантия
для любой последовательности операций.

#### Типичные классы сложности
| Класс | Название | Пример |
|---|---|---|
| O(1) | константная | доступ к элементу массива по индексу, `HashMap.get` в среднем |
| O(log n) | логарифмическая | бинарный поиск, операции `TreeMap` |
| O(n) | линейная | проход по массиву, поиск без индекса |
| O(n log n) | линейно-логарифмическая | `Arrays.sort`, merge sort |
| O(n²) | квадратичная | вложенный цикл по тем же данным, пузырьковая сортировка |
| O(2ⁿ) | экспоненциальная | перебор всех подмножеств |

Разница между классами огромна. При `n = 1 000 000` алгоритм O(n log n) делает
около 20 миллионов операций и укладывается в доли секунды, а O(n²) — около
триллиона, то есть минуты или часы.

Три решения одной задачи — есть ли в массиве дубликаты:
```java
// O(n²) по времени, O(1) по памяти
static boolean hasDuplicateQuadratic(int[] arr) {
    for (int i = 0; i < arr.length; i++)
        for (int j = i + 1; j < arr.length; j++)
            if (arr[i] == arr[j]) return true;
    return false;
}

// O(n log n) по времени, O(n) по памяти на копию (исходный массив не меняем)
static boolean hasDuplicateSorted(int[] arr) {
    int[] copy = arr.clone();
    Arrays.sort(copy);
    for (int i = 1; i < copy.length; i++)
        if (copy[i] == copy[i - 1]) return true;
    return false;
}

// O(n) по времени в среднем, O(n) по памяти
static boolean hasDuplicateSet(int[] arr) {
    Set<Integer> seen = new HashSet<>();
    for (int x : arr)
        if (!seen.add(x)) return true;
    return false;
}
```

Подсчёт операций на массивах без дубликатов (худший случай):
```
n=1 000: вложенные циклы — 499 500 сравнений, HashSet — 1 000 проверок
n=2 000: вложенные циклы — 1 999 000 сравнений, HashSet — 2 000 проверок
n=4 000: вложенные циклы — 7 998 000 сравнений, HashSet — 4 000 проверок
```
При каждом удвоении `n` число сравнений во вложенных циклах растёт ровно
вчетверо — это n(n-1)/2, квадратичный рост. У решения с `HashSet` число
проверок растёт вдвое, линейно, но за это платим памятью и константой: каждая
проверка — вычисление хеша и упаковка `int` в `Integer`.

#### Сложность по памяти (space complexity)
Кроме времени у алгоритма есть потребление памяти сверх входных данных
(auxiliary space). Сортировка на месте вроде heap sort использует O(1)
дополнительной памяти, merge sort — O(n) на вспомогательные массивы, а
рекурсия расходует стек: глубина рекурсии `d` стоит O(d) памяти.

Выбор алгоритма почти всегда компромисс между временем и памятью. Найти
дубликаты можно за O(n²) без дополнительной памяти, за O(n log n) с
сортировкой копии или за O(n) с `HashSet`, который сам занимает O(n) памяти.

#### Декомпозиция задачи
Прежде чем писать код, стоит разбить задачу на подзадачи и проговорить план —
словами или псевдокодом. На живом собеседовании это показывает ход мысли и
страхует от того, чтобы начать писать «с наскока», упереться в забытый
граничный случай и переписывать половину решения.

Хороший порядок такой: уточнить условие и ограничения (размер входа, могут ли
быть дубликаты, пустой ввод), предложить простое решение и оценить его,
затем улучшить, назвать сложность итогового решения и только потом писать
код. Граничные случаи — пустой массив, один элемент, отрицательные числа,
переполнение — стоит проговорить заранее.

Декомпозиция на псевдокоде (так стоит рассуждать вслух перед кодом):
```
найти второй по величине различный элемент массива:
  0. уточнить: что вернуть, если такого нет? могут ли быть дубликаты?
  1. если элементов меньше двух — вернуть «нет ответа»
  2. пройти массив один раз, храня max и secondMax (изначально «пусто»)
  3. для каждого x:
       если x > max — secondMax = max, max = x
       иначе если x != max и x > secondMax — secondMax = x
  4. вернуть secondMax → O(n) по времени, O(1) по памяти
```
Шаг 0 и условие `x != max` — то, что отличает продуманное решение: на массиве
`[5, 5, 3]` без этой проверки вторым максимумом оказалось бы 5.

## Частые вопросы на собеседовании

**Q: Чем отличаются O(), Ω() и Θ()?**
A: `O` — асимптотическая верхняя граница роста функции, `Ω` — нижняя, `Θ` —
точная, когда обе совпадают. Это способ описать рост функции, а не выбор
сценария: и для худшего, и для среднего случая можно дать и O, и Θ. В
повседневной речи «O» обычно используют в значении Θ.

**Q: Что такое амортизированная сложность? Приведите пример.**
A: Это средняя стоимость операции на длинной последовательности, когда
отдельные операции бывают дорогими, но редко. `ArrayList.add` иногда копирует
весь массив за O(n), но ёмкость растёт в 1,5 раза, поэтому суммарно `n`
добавлений стоят O(n), то есть амортизированно O(1) на операцию.

**Q: Почему O(n log n) сортировки считается хорошим результатом?**
A: Для сортировки сравнениями это нижняя граница: любой такой алгоритм в
худшем случае делает Ω(n log n) сравнений, потому что должен различить все n!
перестановок. Быстрее сортируют только алгоритмы, которые используют
структуру ключей, а не сравнения, — например, сортировка подсчётом для
небольшого диапазона целых чисел.

**Q: Как оценить сложность рекурсивного алгоритма?**
A: Нужно понять, сколько рекурсивных вызовов делается на каждом уровне, сколько
уровней и сколько работы на каждом. Бинарный поиск делит задачу пополам и
делает O(1) работы — log n уровней, итого O(log n). Merge sort делит пополам,
но сливает за O(n) на каждом из log n уровней — O(n log n). Наивный рекурсивный
Фибоначчи порождает два вызова на каждом шаге — O(2ⁿ).

## Ловушки и частые ошибки

#### O(n) не всегда быстрее O(n²) на практике
Big-O скрывает константы, и на малых `n` алгоритм с формально худшей
асимптотикой может работать быстрее. Классический пример — insertion sort
быстрее merge sort на маленьких массивах. Поэтому TimSort в Java для коротких
участков (меньше 32 элементов) использует именно сортировку вставками.

#### «O — это худший случай»
Это смешение двух разных вещей. Худший случай — про выбор входных данных, O —
про способ описания роста. Правильно говорить «в худшем случае быстрая
сортировка работает за Θ(n²), в среднем — за Θ(n log n)».

#### Забыть про память и скрытые расходы
Оценивая только время, легко пропустить, что `HashSet<Integer>` на миллион
элементов занимает десятки мегабайт из-за объектов-обёрток и узлов, а
глубокая рекурсия может упасть со `StackOverflowError`. На собеседовании
ожидают, что кандидат сам назовёт компромисс «быстрее, но за счёт памяти».

#### Игнорировать стоимость библиотечных вызовов
`list.contains(x)` внутри цикла по тому же списку — это O(n²), хотя в коде
виден только один цикл. То же с `String.indexOf`, `List.remove(0)` у
`ArrayList` и конкатенацией строк в цикле. Сложность решения складывается из
сложности каждого вызова, а не из числа видимых циклов.
