# База знаний

Личная база знаний для подготовки к собеседованию на позицию senior Java
developer — на замену Obsidian. Живёт как папка `kb/` рядом с сайтом road map
в том же репозитории (`java-senior-roadmap`), не отдельный репозиторий: план
изучения (road map) и конспект по каждой теме (`kb/`) всегда рядом и не
расходятся.

Наполняется по мере прохождения road map. Раздел 1 «Компьютерные основы и
фундамент» — готов полностью, дальше по порядку разделов road map.

## Структура

```
kb/
  _templates/
    topic-template.md        — шаблон для новой темы
  01-fundamentals/           — папка = раздел road map (номер + slug)
    01-os-basics.md          — файл = тема road map (номер + slug)
    02-number-systems-encodings.md
    03-networking-basics.md
    04-git.md
    05-algorithmic-thinking-intro.md
  02-java-core/
    ...
```

Нумерация файлов внутри папки раздела = порядок тем в road map (`01-`, `02-`...),
чтобы сортировка в проводнике/git совпадала с порядком изучения.

## Конвенции

- Один файл — одна Тема (T) road map, не Группа (G) и не Раздел (S). 153 файла на
  весь road map — управляемый объём, при этом каждый файл самодостаточен.
- `topic_slug` в frontmatter = `<раздел>-<тема>-<slug>` (например `01-03-networking-basics`)
  — стабильный ID темы, не зависящий от возможных переименований файла/папки.
  Именно на него в будущем может ссылаться код сайта, если получится сделать
  раздел «Пройтись по базе знаний».
- `related:` в frontmatter — список **чистых `topic_slug`** связанных тем, например
  `- "09-03-heap-vs-stack"`. Именно `topic_slug`, а не путь вида `раздел/файл` —
  формат должен быть стабильным идентификатором темы, не зависящим от того, как
  физически называется файл или папка. Это и есть граф знаний на уровне данных:
  любой скрипт может пройтись по всем .md-файлам, прочитать frontmatter и построить
  граф (узлы = темы, рёбра = `related`), не заглядывая в Obsidian-специфичные
  форматы.
- Можно ссылаться в `related:` на тему, файла которой в `kb/` ещё физически нет
  (раздел road map ещё не написан) — такие ссылки оставляем как задел на будущее,
  а не убираем. Номер темы в `topic_slug` для такой ссылки берём по факту из
  `js/data/<раздел>.js` на сайте (порядок `T(...)` внутри `S(...)`), чтобы ссылка
  сразу была верной, когда файл темы появится.
- В секции «Связанные темы» внутри файла (в отличие от `related:` в frontmatter)
  используются обычные relative-markdown-ссылки на уже существующие файлы
  (`[Название темы](../раздел/файл.md)`); на ещё не написанные темы — обычным
  текстом, без markdown-ссылки (например: «Heap vs Stack в JVM (раздел 9)»), чтобы
  не оставлять на сайте/в редакторе битых ссылок на несуществующие файлы.
- Секции внутри файла — фиксированный список (см. `_templates/topic-template.md`):
  TL;DR → Ключевые концепции (по группам road map) → опционально «под капотом» →
  Примеры → Частые вопросы на собеседовании → Ловушки → Связанные темы → Источники.
  Секцию не пишем, если для темы ей нечего сказать (например «под капотом» пропущена
  во всех темах раздела 1, кроме сетей) — лучше пропустить, чем писать пустую воду.
- `status` в frontmatter (`not-started` / `in-progress` / `reviewed` / `mastered`) —
  задел на будущее: сайт мог бы читать эти статусы и показывать прогресс по базе
  знаний так же, как сейчас показывает прогресс по чекбоксам road map.
- В «Ключевые концепции» почти для каждой темы можно написать что-то в духе «с нуля
  это на собеседовании редко спрашивают» — но это не повод пропускать базовое
  определение самой вещи (что такое context switch, что делает DNS и т.п.) и сразу
  давать только нюанс/«почему». Сначала называем вещь как она есть, потом —
  объяснение уровня senior; без первого второе не на чем держится. Коротко — не
  нужно превращать это в отдельный учебник азов.
- «Ключевые концепции» и «Ловушки» пишутся **прозой, абзацами**, а не bullet-списком
  вида «термин — тире — определение». Внутри абзаца — контекст → зачем это нужно →
  определение → объяснение "как/почему", с обычными связками между предложениями,
  как в статье или главе учебника. Списки (`-`, нумерация) оставляем для мест, где
  это оправдано форматом: команды/код в «Примерах», шаги пошагового механизма в «под
  капотом», перечисление коротких фактов без связного текста между ними — но не как
  основной способ подачи объяснений.
- Абзац — **2-4 предложения**, не больше. Даже если мысль связная и по делу, длинная
  "стена текста" на 6-8 предложений читается тяжело. Как только внутри абзаца
  меняется под-мысль (например: "что это" → "зачем это" → "как проверить на
  примере") — это уже повод начать новый абзац, а не тянуть один. Разбивка на
  абзацы — это форматирование, а не сокращение содержания: резать сам текст не
  нужно, нужно просто чаще ставить пустую строку.
- В «Примерах» — команда/код, потом отдельным блоком **реальный вывод**, потом
  1-3 предложения, что в этом выводе важно (см. `_templates/topic-template.md`).
  Подсмотрено на metanit.com/java/tutorial: там после почти каждого примера кода
  идёт консольный вывод и построчный разбор, что заметно добавляет конкретики —
  не просто «вот команда», а «вот что она реально печатает и что это значит».

- Диаграммы (Mermaid, фенсед-блок ` ```mermaid ` прямо в .md, без отдельных
  файлов-картинок) — добавлять точечно, только там, где есть реальный
  процесс/механизм с шагами, состояниями или структурой, которую полезно
  именно увидеть, а не только прочитать: TCP handshake, состояния потока,
  инкапсуляция, DORA у DHCP, граф коммитов при merge/rebase. Не вставлять
  диаграмму просто чтобы файл выглядел наряднее — если нарисовать нечего,
  значит не надо, и не в каждой теме такое найдётся. Тип диаграммы — под
  механизм: `sequenceDiagram` для обмена сообщениями между сторонами (ARP,
  DORA, handshake), `stateDiagram-v2` для состояний объекта, `flowchart` для
  ветвящегося процесса или сравнения двух схем, `gitGraph` для истории
  коммитов. Диаграмма дополняет текст, а не заменяет его — рядом всегда
  остаётся прозаическое объяснение того же самого, доступное и без рендеринга
  (на случай, если в конкретном редакторе он не настроен). Совместимость:
  GitHub рендерит Mermaid из коробки; в JetBrains IDE (IntelliJ и т.п.) нужно
  один раз включить плагин Mermaid — Settings → Plugins, он в комплекте, но
  выключен по умолчанию; в VS Code без расширения (например, "Markdown
  Preview Mermaid Support") блок останется текстом, а не картинкой.

- Если тема road map большая и заслуживает отдельного углублённого разбора
  сверх одного файла (например, «Основы сетей» — 5 подпунктов программы курса,
  каждый достаточно объёмный сам по себе), можно завести подпапку с тем же
  именем, что было у файла темы (например `03-networking-basics/`), и
  разложить материал на несколько файлов внутри неё. Файл, который раньше был
  темой (`03-networking-basics.md`), становится `00-index.md` этой подпапки —
  сохраняет тот же `topic_slug` (чтобы старые `related:`-ссылки на него не
  ломались) и остаётся кратким обзорным конспектом «в среднем достаточно для
  собеседования», а более глубокие вопросы выносятся в отдельные пронумерованные
  файлы (`01-...`, `02-...`) со своими собственными `topic_slug` вида
  `<родительский-slug>-01-...`. `00-index.md` должен явно ссылаться на все файлы
  подпапки (например, разделом «Материалы для углублённого изучения»), а каждый
  файл подпапки — ссылаться обратно на `00-index.md` и на соседей в «Связанные
  темы». Это исключение из правила «один файл — одна Тема» и оправдано только
  для действительно объёмных тем — не плодить подпапки без необходимости.

## Что дальше (не сейчас)

- Когда файлов наберётся достаточно, можно написать скрипт (Node/Python), который
  читает frontmatter всех .md, строит граф по `related` и рендерит его (например,
  Mermaid-диаграммой или простым force-directed графом) — либо отдельной страницей,
  либо прямо внутри сайта road map через кнопку «Пройтись по базе знаний».
- До этого момента граф существует только как данные (`related:` + обычные
  markdown-ссылки в конце файла) — этого достаточно, чтобы им пользоваться руками
  уже сейчас, без какого-либо инструмента.
